# Output styles: Bureau feature design

**Date**: 2026-03-31
**Status**: Proposed design
**Scope**: Make `output_style` a first-class Bureau feature, with native Claude Code output-style support and equivalent always-on behavior for Codex, Gemini CLI, and OpenCode.

## Decision

- Bureau will add a top-level `output_style` config key with user experience intentionally parallel to `code_standards`.

- Bureau will ship a stock seed file at `protocols/context/static/ops/output-style.md`.

    - This file will be Bureau's copy of `think/workbench/CLAUDE.md`, adapted only as needed for Bureau ownership, disclaimers, and transport compatibility.

- Bureau setup will compile the resolved `output_style` source files into a single deployed runtime artifact at `~/.config/bureau/protocols/output-style.md`.

    - This deployed root-level file is the only file consumed by the CLI-specific adapters.

- Claude Code will use its native output-styles mechanism.

    - Bureau will install a generated Claude output-style file under `~/.claude/output-styles/`.
    - Bureau will select that style through Claude settings at **user scope**, not project-local scope.

- Codex, Gemini CLI, and OpenCode will use Bureau-managed emulation.

    - They will read the full deployed style file once per session.
    - They will **not** re-inject the full style on every turn.
    - Per-turn reinjection stays compact: the existing hub remains the only repeatedly injected artifact, and it carries a short reminder that the output style loaded at session start remains active for the session.

## Why this design

- It preserves a **single user-facing concept**: "Bureau output style".

- It keeps a **single source of truth** for style content while honestly acknowledging that the upstream CLIs do not expose the same configuration surface.

- It uses Claude Code's native mechanism where it exists.

    - This is the closest possible match to Claude's intended semantics.

- It avoids context explosion for Codex and Gemini.

    - The style is loaded once, not appended on every prompt.

- It gives OpenCode a clean integration path without inventing a fake native output-style feature.

## Goals

- Make Bureau output style feel conceptually equivalent to Claude Code's "always active once selected" output-style behavior.

- Make `output_style` feel operationally equivalent to `code_standards` at the Bureau config layer.

    - Same override model
    - Same path resolution rules
    - Same "Bureau ships a default, user can replace it" ergonomics

- Keep the runtime style payload stable and bounded.

- Avoid requiring users to manage four separate style definitions.

- Keep implementation surfaces explicit and testable.

## Non-goals

- Do **not** make non-Claude CLIs pretend they have a native system-prompt output-style feature.

    - They do not.
    - Bureau should emulate equivalent behavior, not claim feature parity at the implementation level.

- Do **not** re-inject the full style file on every turn for Codex or Gemini.

- Do **not** make `output_style` task-routed like code standards.

    - It is always-on session behavior, not a task-specific standards document.

- Do **not** let the runtime deployed file become an ad hoc hand-edited configuration surface.

    - User customization should flow through the config key, not silent manual edits to the generated artifact.

## User model

- Users configure Bureau output style through a new top-level key:

```yaml
output_style:
  - protocols/context/static/ops/output-style.md
```

- As with `code_standards`, the value is a list of markdown files.

- The list is resolved in order, then compiled into a single runtime artifact.

- If the key is absent, Bureau uses the stock seed file at `protocols/context/static/ops/output-style.md`.

- Users do **not** point Claude directly at arbitrary style files.

    - They point Bureau at one or more source files.
    - Bureau compiles and installs the resulting style into each CLI's appropriate delivery mechanism.

## File model

### Repo-owned seed file

- `protocols/context/static/ops/output-style.md`

- Purpose:

    - Bureau's shipped default style content
    - The canonical in-repo seed for `output_style`

- Constraints:

    - Plain markdown instruction text
    - No Claude-specific frontmatter
    - Must be valid as a standalone Bureau style source

### Deployed runtime artifact

- `~/.config/bureau/protocols/output-style.md`

- Purpose:

    - The compiled Bureau-managed runtime style artifact
    - The single stable path used by all adapters

- Constraints:

    - Generated by Bureau setup
    - Safe to read from all supported CLIs
    - Plain markdown instruction text
    - No Claude-specific frontmatter

### Claude-native generated wrapper

- `~/.claude/output-styles/bureau.md` or equivalent Bureau-owned file name

- Purpose:

    - Claude-native wrapper around the deployed Bureau runtime artifact

- Constraints:

    - Contains Claude output-style frontmatter
    - Generated from `~/.config/bureau/protocols/output-style.md`
    - Not treated as the user-facing source of truth

## Config semantics

### New key

- Add top-level `output_style` to Bureau configuration.

- It should be documented directly alongside `code_standards` in [CONFIGURATION.md](/Users/danielakbarzadeh/code/bureau-concierge/docs/CONFIGURATION.md).

### Resolution order

- Resolution should intentionally parallel `code_standards`, but the result is always compiled into one runtime file.

- Proposed behavior:

    1. If `output_style` is set, resolve those files in order and compile them into `~/.config/bureau/protocols/output-style.md`.
    2. Otherwise, compile the stock Bureau seed file at `protocols/context/static/ops/output-style.md` into `~/.config/bureau/protocols/output-style.md`.

- Unlike today's `code_standards` convention, the deployed root file should be treated as the **generated runtime result**, not as an informal alternate source location.

    - This avoids ambiguity about whether the root file is an input or an output.

### Path resolution rules

- Use the same rules as `code_standards`:

    - `~/...` expands to `$HOME`
    - absolute paths are used as-is
    - relative paths resolve from the Bureau repository root

### Aggregation semantics

- If `output_style` contains multiple files, Bureau concatenates them in list order into the deployed runtime artifact.

- The generated file should begin with a Bureau-owned preamble such as:

    - generated file notice
    - source file list
    - warning not to hand-edit the runtime artifact

- Bureau should preserve the body content of source files as faithfully as possible.

- Bureau should **not** require source files to use Claude-specific frontmatter.

    - The Claude adapter adds frontmatter later.

## Session semantics

- Output style is a **session-level always-on instruction**.

- The full style content is loaded once per session.

- Style changes are picked up on a **new session**.

- Bureau should document this uniformly across all CLIs, even though the transport mechanisms differ.

- Bureau should not attempt hot-reload semantics for output style.

    - That would be inconsistent with Claude's native model and would create confusing partial-state behavior elsewhere.

## Per-CLI adapters

### Claude Code

- Claude should use the native output-styles feature.

- Adapter responsibilities:

    - Read `~/.config/bureau/protocols/output-style.md`
    - Wrap it in Claude output-style frontmatter
    - Install the generated style file into `~/.claude/output-styles/`
    - Set Claude's `outputStyle` setting at **user scope**

- The generated Claude wrapper should include:

```yaml
---
name: Bureau
description: Bureau-managed output style
keep-coding-instructions: true
---
```

- `keep-coding-instructions: true` is required.

    - Bureau's output style is meant to shape response structure and tone.
    - It is **not** meant to disable Claude's coding-specific instructions.

- Settings scope:

    - Claude Code supports user-scoped settings in `~/.claude/settings.json`.
    - Bureau should manage `outputStyle` there because Bureau itself is a user-scoped setup system.
    - Bureau should **not** rely on project-local `.claude/settings.local.json` for its primary integration.

- Fallback behavior:

    - If native style installation fails, Bureau may log a warning and optionally fall back to regular context-file behavior for that session.
    - The design goal, however, is native install first.

### Codex

- Codex gets Bureau output-style behavior through startup context, not native system-prompt replacement.

- Adapter responsibilities:

    - Ensure the generated Bureau `AGENTS.md` tells Codex to read `~/.config/bureau/protocols/output-style.md` at session start
    - Preserve existing per-turn hook behavior for `ops-hub.md`
    - Avoid re-reading the full style every turn

- Important constraint:

    - The Codex hook must **not** cat the full style file on every prompt.

- Reinforcement model:

    - Session start loads the full style once.
    - Per-turn hook re-injects only the compact hub.
    - The hub contains a short reminder that the output style loaded at session start remains active for the session and should not be re-read each turn.

### Gemini CLI

- Gemini uses the same model as Codex.

- Adapter responsibilities:

    - Ensure the generated Bureau `AGENTS.md` tells Gemini to read `~/.config/bureau/protocols/output-style.md` at session start
    - Preserve existing hook-based reinjection of the compact hub only
    - Keep the style payload out of the per-turn hook output

- This makes Gemini behavior operationally similar to Claude's "always active once selected" semantics without trying to fake native system-prompt replacement.

### OpenCode

- OpenCode should consume the deployed Bureau runtime artifact through its `instructions` array.

- Adapter responsibilities:

    - Add `~/.config/bureau/protocols/output-style.md` to the generated OpenCode `instructions` list
    - Keep that path stable so setup refreshes do not require downstream path churn

- OpenCode does not need a separate per-turn reminder mechanism if its instructions are already session-scoped.

- Changes should take effect on the next OpenCode session.

## Hub behavior

- `ops-hub.md` should **not** route agents to the full output-style file.

    - If it did, the hook reminder mechanism would repeatedly tell agents to read the full file.
    - That would create unnecessary context growth and would undermine the bounded-payload requirement.

- Instead, `ops-hub.md` should carry a tiny reminder block such as:

```xml
<output-style-reminder>
  The Bureau output style loaded at session start from {{PROTOCOLS_DIR}}/output-style.md remains active for this session.
  Do not re-read it every turn.
  Changes take effect on a new session unless explicitly told to refresh it.
</output-style-reminder>
```

- This keeps hook reinjection compact and semantically clear.

## Template changes

### `AGENTS.template.md`

- This file should change from "single must-read file" to "must-read files" for Codex and Gemini.

- It should instruct the model to read:

    - `{{PROTOCOLS_DIR}}/output-style.md`
    - `{{PROTOCOLS_DIR}}/ops-hub.md`

- The template should make the distinction explicit:

    - `output-style.md` = session-level always-on response style
    - `ops-hub.md` = operational router for Bureau context

### `CLAUDE.template.md`

- Claude should continue to read the hub.

- It should **not** load the full output-style file as an extra must-read if Bureau has already installed the style natively.

    - Loading both would duplicate instructions and weaken the value of the native integration.

- Claude-facing docs may still mention that Bureau has installed a native output style, but the full style file should not be added to the must-read list for Claude.

## OpenCode template changes

- `protocols/config/templates/opencode.json` should add the deployed runtime artifact to `instructions`.

- This requires the OpenCode render path to support `{{PROTOCOLS_DIR}}` substitution in addition to `{{REPO_ROOT}}`, or otherwise receive the resolved protocols path explicitly.

- The important invariant is:

    - OpenCode must read the deployed runtime artifact at `~/.config/bureau/protocols/output-style.md`, not the static seed file in the repo.

## Setup flow

### `set-up-protocols.sh`

- Add a Bureau-managed seed constant for `output-style.md`.

- Install behavior:

    1. Resolve `output_style` config.
    2. If configured, resolve all paths and compile them into `~/.config/bureau/protocols/output-style.md`.
    3. Otherwise, compile the stock seed file from `protocols/context/static/ops/output-style.md` into `~/.config/bureau/protocols/output-style.md`.
    4. Continue deploying `ops-hub.md` and spoke files as today.
    5. Generate Codex/Gemini templates with the stable deployed root path.
    6. Trigger Claude/OpenCode adapter steps downstream.

- The generated runtime file should be Bureau-owned and reproducible.

### Claude installer step

- Add a Bureau-owned setup step that:

    - creates the native wrapper file under `~/.claude/output-styles/`
    - writes or merges the user-scoped Claude setting that selects it

- This can live in `set-up-protocols.sh` directly or in a dedicated helper script.

    - A helper script is cleaner if Claude settings merging becomes non-trivial.

### OpenCode setup step

- Extend the OpenCode template/render pipeline so the generated config includes the deployed runtime artifact in its `instructions` array.

- This belongs to the OpenCode config path, not to hook configuration.

## Ownership and update model

- `protocols/context/static/ops/output-style.md` is repo-owned source.

- `~/.config/bureau/protocols/output-style.md` is Bureau-generated runtime output.

- The Claude-native file in `~/.claude/output-styles/` is Bureau-generated adapter output.

- Users should customize the feature through the `output_style` config key, not by editing generated runtime files in place.

- Setup modes:

    - default mode: generate the runtime artifact if missing
    - update mode: regenerate the runtime artifact from current config
    - force mode: overwrite Bureau-generated adapter outputs without backup
    - bare mode: remove the generated runtime artifact and remove Bureau adapter integration where applicable

## Failure modes and safeguards

### Context blow-up in Codex or Gemini

- Risk:

    - Re-injecting the full style file on every turn would cause the conversation context to grow unnecessarily.

- Safeguard:

    - Never include the full output-style file in the per-turn hook output.
    - Only re-inject the compact hub reminder.

### Drift between Claude native style and Bureau runtime artifact

- Risk:

    - Claude's installed native style could become stale if the deployed runtime artifact changes but the native wrapper is not refreshed.

- Safeguard:

    - Refresh the Claude-native wrapper on every relevant setup run.
    - Keep the wrapper mechanically generated from the deployed runtime artifact.

### Ambiguity about input vs output files

- Risk:

    - Users may confuse `~/.config/bureau/protocols/output-style.md` with a source file they should edit manually.

- Safeguard:

    - Add a generated-file preamble.
    - Document that customization belongs in `output_style` config inputs.

### Claude settings scope mismatch

- Risk:

    - Writing the selected style at project-local scope would make Bureau behavior inconsistent across repositories.

- Safeguard:

    - Use Claude user-scope settings as the primary integration point.

### OpenCode path mismatch

- Risk:

    - OpenCode could read the repo seed file instead of the deployed runtime artifact, causing behavior drift from the other CLIs.

- Safeguard:

    - Explicitly wire OpenCode to the deployed root runtime file, not the repo seed.

## Alternatives considered

### Pure Bureau emulation for all CLIs, including Claude

- Rejected because Claude has a native output-style feature and Bureau should use it where available.

- Also rejected because `CLAUDE.md`-style user-message injection is not semantically the same as native system-prompt output styles.

### Native Claude feature plus full-style per-turn reinjection for Codex and Gemini

- Rejected because it is unsafe for context growth.

- The behavioral gain is not worth the prompt-size cost.

### Treat output style as another `ops/` routed spoke

- Rejected because task-routed spokes are the wrong abstraction for an always-on session-level instruction.

- The repo seed file should still live in `ops/` for consistency with Bureau's shipped protocol sources, but the deployed runtime artifact should live at the root of the user-scoped protocols directory.

### Separate concepts for Claude vs non-Claude CLIs

- Rejected because it would force users to learn two features for one intent.

- Bureau should present one conceptual feature with different transport adapters underneath.

## Test plan

- Protocol deployment tests:

    - deployed runtime artifact exists at `~/.config/bureau/protocols/output-style.md`
    - default generation uses the stock seed file when `output_style` is unset
    - configured generation concatenates multiple source files in order

- Template tests:

    - Codex/Gemini generated `AGENTS.md` includes `output-style.md` in the must-read file list
    - Claude generated `CLAUDE.md` does **not** duplicate the full output-style file in must-read instructions

- Hook tests:

    - Codex/Gemini hooks still re-inject the hub only
    - hub reminder text exists and remains compact

- Claude adapter tests:

    - native wrapper file is generated with valid frontmatter
    - `keep-coding-instructions: true` is present
    - user-scoped Claude setting selects the Bureau style

- OpenCode tests:

    - generated config includes the deployed runtime artifact in `instructions`
    - render pipeline substitutes the resolved protocols path correctly

## Done criteria

- Bureau exposes a documented top-level `output_style` config key.

- Bureau ships a stock seed file at `protocols/context/static/ops/output-style.md`.

- Setup compiles the resolved style sources into `~/.config/bureau/protocols/output-style.md`.

- Claude uses a native installed output style generated from the deployed runtime artifact.

- Codex and Gemini load the full style once per session and only receive compact reminder reinjection thereafter.

- OpenCode reads the deployed runtime artifact through its `instructions` array.

- No supported CLI depends on reading the repo seed file directly at runtime.

- The design is documented clearly enough that implementation can proceed without inventing missing semantics mid-stream.
